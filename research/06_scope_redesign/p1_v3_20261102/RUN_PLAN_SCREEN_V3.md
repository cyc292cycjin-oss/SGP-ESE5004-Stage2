## 2. 顺序

主结果两次优先，三个阶段，每阶段内两条通道：

| 阶段 | 通道 A | 通道 B |
|---|---|---|
| 1 | V1 | V2 |
| 2 | V4 | V5 |
| 3 | V3 | — |

- 容器 ≥ 33 核时两条通道并行（WLS 最多 2 个会话），否则一条通道依次运行：V1 → V2 → V4 → V5 → V3。
- 两次求解之间、阶段之间间隔 ≥ 330 s。
- 每个阶段结束后做批参照与重评。V1、V2 的账本齐备后写 `BATCH_REFERENCE.json`，后面的运行直接用它。

## 4. 实例规格

单会话峰值：DFX V1 22.29 GiB × 1.05（LP 增量）≈ 23.5 GiB。后处理峰值约 11 GiB。

| 项 | 硬下限（预检） | 建议 | 依据 |
|---|---:|---:|---|
| 核数 | 17 | ≥ 33 | Threads 16 + 后处理 1；并行 2 × 16 + 1 |
| 内存 | 64 GiB | 92 GiB 以上 | 串行 23.5 + 11 ≈ 35 GiB；并行 2 × 23.5 + 11 ≈ 58 GiB |
| 数据盘 | 90 GB | ≥ 100 GB | DFX 两次运行实测用 28 GB；5 次按比例约 70 GB，加环境和包 |

DFX 的 45 GB 下限是估算值，实测已用 28 GB，5 次运行不够，所以在定义文件里改为 90 GB。

实测的 25 核 / 92 GiB（West-B 8470Q）满足下限，但只能串行。

## 7. 停止规则

沿用 `RUN_PLAN_DFX.md` 第 3.3 节，V1、V2 是批参照：

| 情况 | 动作 |
|---|---|
| 任一运行 G2 不通过 | 停批 |
| V1 或 V2 无返回解，或 C1 (a) 不通过 | 停批 |
| V3、V4、V5 无返回解，或 C1 (a) 不通过 | 记为不可用，其余继续 |
| 只有 C1 (b) / (c) 不通过 | 不停 |
| 墙钟止损 | 终止该进程组，不重试 |
| 中断、网络 SHA256 不符、缺输入、有残留求解进程 | 安全停止，等用户 |

停批后不启动新求解，已在运行的求解跑完并做后处理。**不重试、不改参数，由用户决定。**

`no_new_xb` 在 365×24h 下可能仍是 suboptimal。按决定 4 以 C1 (a)(b)(c) 和 GATES_V6 判定，第 120 项 `accepted` 只作数值信息。
