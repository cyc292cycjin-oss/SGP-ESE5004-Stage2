## A2 降低内存与风险的手段（每项都要有测量或测试支撑；不改变解）

1. **linopy 传模型的方式：** 现在 `Model.solve(io_api=None)` 先把 LP 文件写到 `TMPDIR`，再由 Gurobi 读入。测量改为直接经 gurobipy 传入（`io_api="direct"` 或等价方式）对峰值内存、耗时与磁盘的影响。
   - **只有满足等价判据才采用：** 同一网络两种方式交给 Gurobi 的模型完全相同。优先比较 Gurobi 的 `Fingerprint` 属性；比较不了时，比较导出的 LP 数组与 56×3h 的完整求解结果（目标值、终止状态、迭代数逐位相同）。
   - 不满足就不采用，只报告测量结果。
2. **Gurobi 软内存上限：** 评估 `SoftMemLimit`（或 Gurobi 12 中的等价参数）。超限时 Gurobi 应在安全点停下，返回内存超限状态，而不是被系统强杀、什么都不留。
   - 在 56×3h 上用一个很小的上限实测：状态码、回执内容、脚本的分类（应归入"无返回解"，并按规则处理）。
   - 证明不触发时，解与不设上限时逐位相同。
   - 若采用，它属于运行保护参数，不是求解算法参数。在计划中登记为"第四批每个运行设 SoftMemLimit = 实例内存配额的 85 %"（或你按测量给出的比例），并写明理由。
3. **串行与并行：** 核数不是瓶颈，两个运行串行即可在 ≥ 25 核的机器上进行。按 A1 的结论写出并行条件（见 A4）。
4. **其他：** 如果发现别的能显著降低内存、又不改变解的办法（例如求解阶段释放不再需要的 Python 对象），同样先测量、再证明等价，然后才采用；否则只报告。

## A3 保护性代码修改

1. **求解结果先落盘，再记账（最重要）：** 现在求解进程内的求解后账本或导出一旦抛异常，回执会带 `failure`、没有终止状态，按规则被当作"无返回解"处理（M10A F12、M10R 发现 2）。在 2920×3h 上，这意味着一天多的求解白费。改为：
   - 求解返回后，先写出终止状态、目标值、原始 / 对偶目标、迭代信息与回执，以及解与对偶（数组、求解后网络），然后再做账本、B16、成本拆分等求解后步骤；
   - 求解后步骤的异常写入回执的独立字段（例如 `post_solve_errors`），**不改变终止状态与"有返回解"的判定**；
   - G2.3 照常核对导出完整性：缺什么就报什么，事后可用 `--repost` 补做。
   - **回归：** 56×3h 的 M08b 冒烟一体化 / 不互联、M12b 去一国、M10R 三次求解，重新跑后处理链，结果逐位相同。再用替身测试证明：注入求解后异常时，回执保留终止状态与解，分类不是"无返回解"。
2. **路径规范化：** 运行脚本的 `--into`、`--use`、`--arrays` 以及第四批脚本的同类参数，一律转成完整路径。补测试：相对路径与完整路径结果相同（M10S1 的执行偏差）。
3. **conda 镜像：** `install_env.sh` 支持按频道分别替换镜像（conda-forge / bioconda / gurobi 各自的地址），不支持的频道保持直连。只检查 URL 格式与一两个包能否访问，不全量下载。M10 发现 6。
4. 以上修改都不改变第三批脚本的批次模式行为；第三批的替身测试必须全部通过。
